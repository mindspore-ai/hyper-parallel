## 1. 规划范围与总体安排

本规划聚焦 HyperParallel 的预训练与微调能力，推理和 RL 暂不纳入。
围绕 **易用性与解耦、复杂模型并行、十万卡高可用、多核并行开发框架** 四项核心能力，
按照 **2027 年趋势 → 关键挑战 → 技术竞争力目标 → 具体工作** 组织建设。

四项能力的分工如下：

- **Codegen**：根据模型、用户需求、并行策略和硬件能力生成专属训练实现，支持 Agent RSI 和用户二次开发。
- **多维并行**：决定复杂模型和动态负载如何在设备、节点与超节点之间分配。
- **高可用运行时**：保护训练状态，在故障与恢复过程中持续积累有效训练进度。
- **多核并行开发框架**：表达并调度核级计算与通信，提高执行性能和新算子开发效率。

每项能力设置五个工作包，共形成二十个工作包。数值正确性、收敛质量、可诊断性和性能回归控制，
作为四项能力共同的交付与验收要求。

十万卡按单训练作业的设计规模讨论，设计与仿真、可用规模实机演练、十万卡实机联合验证分别验收。
具体量化阈值、模型覆盖范围、资源投入和交付排期需在立项阶段确定。

## 3. 能力一：易用性与解耦——面向 Agent RSI 的个性化训练框架生成

### 3.1 2027 年趋势

**模型表达与执行解耦的公开信号。** Hugging Face 的 Modular Transformers 采用模块化源文件生成完整模型实现，
兼顾代码复用和可读的模型文件。2026 年 10 月的 TorchTitan 更新进一步强调显式训练图、跨模块优化及图级调试。
这些进展表明，生成与编译机制正在成为连接模型开发和高性能执行的重要手段。
参考：[Modular Transformers](https://huggingface.co/docs/transformers/main/modular_transformers)、
[TorchTitan 2026 年 10 月更新](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl/)。

**RSI for Infra 的近期案例。** 截至 2026 年 10 月 26 日，公开实践已覆盖 Agent 对算子、编译及基础设施算法的持续优化。
下表区分实现的迭代搜索、优化经验复用和优化 Agent 自身能力提升，保留各案例的验证范围。

| 案例与公开时间 | 优化闭环与公开结果 | 对 HyperParallel 的启示与证据边界 |
| --- | --- | --- |
| [Meta KernelEvolve](https://engineering.fb.com/2026/04/02/developer-tools/kernelevolve-how-metas-ranking-engineer-agent-optimizes-ai-infrastructure/)，2026-04-02 | 将生成、编译、正确性检查、性能诊断和搜索接成闭环；积累跨任务经验，并用优化轨迹后训练专用模型。官方报告某广告模型在 MTIA 上训练吞吐提升超过 25%，算子优化由数周缩短至数小时。 | 支撑“优化基础设施—积累实测反馈—改善后续优化能力”的路线。需建设可执行评测和经验库；所报收益限定于对应模型、硬件和内部流程。 |
| [Google AlphaEvolve 基础设施进展](https://deepmind.google/blog/alphaevolve-impact/)，2026-05-07；[云服务正式可用](https://cloud.google.com/blog/products/ai-machine-learning/alphaevolve-is-available-for-everyone)，2026-07-09 | 通过种子程序、可执行评分函数与演化搜索持续优化代码。官方披露其用于 TPU 设计、缓存替换和编译优化；云服务将问题定义、评分、优化和应用组织为可复用流程。 | 将并行策略、调度和组件选择表达为有质量约束的可搜索问题；这是从案例推导的建设方向，相关结果未直接验证 HyperParallel 的训练策略搜索或完整框架生成。 |
| [PyTorch KernelAgent](https://pytorch.org/blog/kernelagent-hardware-guided-gpu-kernel-optimization-via-multi-agent-orchestration/)，2026-03-06 | 用真实硬件 profiling 驱动诊断、改写、验证和再次测量，并通过共享记忆复用每轮经验。在 H100 的 100 个 KernelBench L1 任务上，相对默认 torch.compile 获得 1.56× 几何平均加速。 | Agent 需要可归因的硬件反馈和明确停止条件。结果针对前向算子；对照使用静态形状并关闭 CUDA Graph，训练前反向及端到端收益需另行验证。 |
| [Intel Day-0 Kernel Bring-Up，PyTorch Conference 2026](https://pytorch.org/blog/open-research-tooling-optimization-at-pytorch-conference-north-america-2026/)，2026-09-16 公布议程，报告安排于 10-20 | 官方议程介绍以分阶段 Agent 和长期记忆串联 profiling、分析、代码生成、验证、修复及评测，并报告将算子开发周期从数周缩短至隔夜运行。 | 提示应把新硬件适配组织为可重复执行的开发流程。当前引用为大会议程摘要，具体任务、资源预算和质量口径仍需核验，不据此设定本项目量化目标。 |

这些案例提供了 RSI for Infra 的不同环节：实现优化、经验积累，以及利用轨迹改进优化 Agent。
其中 KernelEvolve 明确披露了专用模型后训练；其他案例中的迭代搜索或共享记忆本身不足以证明模型能力发生递归提升。
本规划据此优先建设可验证的优化环境、可修改的生成产物和可复用的实验反馈，并分别衡量产物收益与优化过程的效率改善。

**规划判断。** 面向 2027 年，训练基础设施需要同时服务人工开发和 Agent 驱动的持续优化。
不同用户的模型、数据、硬件及训练目标，需要转换为可执行、可验证、可持续修改的训练实现。
本规划将 Agent RSI 的支撑重点落在“生成—验证—硬件评测—诊断改进—经验复用”闭环上。
Codegen 提供可追踪、可重新生成的修改对象，多维并行和多核框架提供可组合的优化空间，
统一评测反馈用于筛选候选实现并改善后续搜索；以未参与经验积累的任务检验复用效果。

### 3.2 关键挑战

一个模型需要覆盖多种并行组合、硬件和高性能组件。
这些差异进入模型源码后，模型升级会牵动通信逻辑、模块替换、权重映射和数值验证，维护成本随组合数量增长。
Agent 自动优化需要可理解的契约和可归因的反馈，用户二次开发则需要清晰的执行边界和能够持续维护的定制入口。

易用性应体现为模型开发者能够保持清晰的模型表达，分布式与硬件优化能够独立演进，
并通过生成机制可靠地组合为适合具体用户的训练框架。

### 3.3 技术竞争力目标

> 以 Codegen 为核心，实现模型、并行策略与执行实现解耦，支持 Agent 根据用户需求生成专属训练框架，
> 并通过正确性与性能反馈持续优化；提供清晰、可修改的生成代码和扩展接口，降低二次开发与升级维护成本。

| 竞争力 | 用户价值 | 建设重点 |
| --- | --- | --- |
| 亲和 Agent RSI | Agent 能够持续完成生成、验证、评测和改进，将优化经验用于后续迭代。 | 结构化模型与策略描述、可追踪变更、自动正确性验证、可归因的性能反馈和有效经验复用。 |
| 为每个用户生成专属训练框架 | 根据用户的模型、数据、硬件、集群拓扑和训练目标，生成适合其场景的训练实现及组件组合。 | 从模型代码生成扩展到训练组件装配、并行执行实现和运行配置生成，复用公共运行时与高性能组件。 |
| 便于二次开发 | 用户能够理解、调试和修改模型执行过程，接入自定义模块、损失函数、优化器和训练逻辑。 | 可读的生成代码、清晰执行边界、稳定扩展点和可追踪的定制修改机制，使用户修改随重新生成及版本升级持续维护。 |

**现有基础。** 仓库 Codegen 已能将并行契约、边界通信和模块替换固化到生成产物中，
运行时读取冻结计划并执行分片。2027 年围绕覆盖范围、个性化装配和工程完整性继续建设。
参考：[Codegen 使用指南](guide/codegen.zh.md)。

## 4. 能力二：面向稀疏 MoE、长序列、全模态与世界模型的并行竞争力

### 4.1 2027 年趋势

**公开信号。** Dynamic Context Parallelism 的公开工作说明，变长文本和视频训练中，
相同 token 总量仍可能对应不同计算量，进而产生数据并行等待和流水线气泡。
MoE Parallel Folding 研究采用注意力层与专家层不同的并行配置。
2026 年 10 月 NVIDIA 更新 Cosmos 时，进一步扩展了多模态、多传感器数据处理和世界模型训练工具。
参考：[动态上下文并行](https://developer.nvidia.com/blog/speeding-up-variable-length-training-with-dynamic-context-parallelism-and-nvidia-megatron-core/)、
[MoE Parallel Folding](https://arxiv.org/abs/2504.14960)、
[Cosmos 2026 年 10 月更新](https://blogs.nvidia.com/blog/cosmos-open-train-evaluate-deploy-world-models/)。

**规划判断。** 稀疏 MoE、长序列、全模态和世界模型会叠加于同一训练任务。
模型结构、输入形态和任务目标共同决定计算、通信及内存需求，需要共享的成本模型、策略规划与动态调度能力。

### 4.2 关键挑战

| 重点场景 | 核心挑战 | 对应并行建设方向 |
| --- | --- | --- |
| 稀疏 MoE | 专家路由不均、不规则计算、All-to-All 热点，以及专家参数规模与激活计算量不匹配。 | 拓扑感知 EP、专家放置和执行均衡、dispatch/combine 通算协同，与 TP、CP、PP、FSDP 联合优化。 |
| 长序列 | 激活及通信开销增长；因果、稀疏、混合注意力具有不同切分语义和计算分布。 | 面向不同注意力结构的 CP，结合变长 packing、计算均衡、重计算和卸载联合规划。 |
| 全模态 | 文本、图像、音频和视频分支开销差异大，样本形状动态，跨模态对齐及 loss 语义复杂。 | 编码器与主干协同并行、模态感知数据组织、分支与流水线均衡，保持对齐及损失计算正确。 |
| 世界模型 | 视频、时空结构、多视角和动作条件预测带来更大的激活及复杂计算图。 | 针对目标架构探索时间、空间、视角等维度切分，支持扩散、流匹配或自回归训练路径的并行与内存优化。 |

固定样本数或 token 数不能完整描述资源开销。
按最坏情况配置会降低利用率，按平均情况配置可能无法承受显存峰值；
局部算子加速还可能被通信等待、数据搬运和调度开销抵消。

### 4.3 技术竞争力目标

> 建立面向复杂模型结构和动态训练负载的多维并行体系，在既定资源与质量约束下扩大可训练规模，
> 并持续提高端到端训练效率，使优化能够在目标模型、硬件与集群规模之间复用。

### 4.4 具体工作

| 编号 | 工作包 | 具体工作 | 交付物 |
| --- | --- | --- | --- |
| 2.1 | 硬件、负载与内存建模 | 实测目标 GPU/NPU 计算、显存和分层互联特征；描述专家路由、序列长度、模态组成及 micro-batch 对计算、通信和内存峰值的影响。 | 硬件与负载画像、校准后的成本模型、峰值内存模型和预测误差报告。 |
| 2.2 | 多维并行与资源联合规划 | 联合选择 DP/FSDP、TP、EP、CP、PP、rank 映射、重计算、卸载和预取；考虑超节点内外通信差异；将搜索结果映射为可执行方案。 | 拓扑感知策略、资源预算下的训练配方、容量与吞吐权衡结果。 |
| 2.3 | 稀疏 MoE 与长序列执行优化 | 优化专家放置、dispatch/combine 和通信热点；支持目标注意力结构的 CP；完善变长 packing、分桶与负载分配，控制通信和流水线等待。 | MoE 与长序列优化路径、EP/CP 均衡报告、极端路由与长度分布回归集。 |
| 2.4 | 全模态与世界模型训练支撑 | 建设编码器和主干协同执行、模态分支和 stage 均衡；针对代表世界模型实现时空等维度切分及内存优化；校验样本对齐和 loss 语义。 | 代表架构的训练配方、模态与时空负载基准、正确性和性能证据。 |
| 2.5 | 端到端性能与能力边界验证 | 在固定资源下增加模型规模、上下文长度及模态负载；测量启动编译成本、稳态吞吐和扩展效率；与同硬件方案对比并纳入发布回归。 | 可训练能力边界、性能基线、回归流程和可复现对比报告。 |

### 4.5 验收指标

- 固定资源下可训练的模型规模、序列长度、分辨率、视频长度及模态组合。
- 同硬件、同数据和同质量要求下的有效吞吐、固定训练量所需卡时及扩展效率。
- EP/CP 计算耗时最大比、负载不均等待占比、峰值显存和长尾性能。
- 极端长度分布、专家倾斜和资源接近上限时的行为与可运行边界。

**负载均衡统计口径：** 对同一层、同一 micro-batch、同一并行组，定义最大负载比为
`R(x) = max(x_i) / mean(x_i)`，变异系数为 `CV(x) = std(x_i) / mean(x_i)`。
先按上述粒度计算，再汇总 P50、P95 和最差值。无有效负载时单独标记，不以零均值计算比值。

MoE 区分专家路由分布与 EP rank 计算耗时；CP 按实际注意力计算和设备耗时评价，不能只比较 token 数。
计算耗时应使用设备端计时并与同步等待分开，前向和反向分别统计。
端到端收益需计入均衡策略的额外通信、重分片和调度成本；有效 token 排除 padding 和并行复制计数。
丢弃率、模型数值及收敛质量作为共同约束，不以减少有效计算换取表面均衡。

## 5. 能力三：面向十万卡训练的高可用运行时

### 5.1 2027 年趋势

**公开信号。** 2026 年 FT-HSDP 论文报告了约 9.8 万张 H100 的容错实验，
采用数据并行副本作为容错单位，使故障副本退出恢复期间，其余副本能够继续训练。
这为十万卡量级的局部恢复和持续训练提供了公开工程依据。
参考：[FT-HSDP 论文](https://arxiv.org/html/2602.00277v1)。

**证据边界。** 论文 §6.2 明确将全规模实验仅开展一次且持续时间较短归因于全规模实验的资源负担，
并在 256 张 H100 上开展更充分的训练质量对照实验。§6.1 还说明，修复后再次进行十万卡测试需等待相应资源可用。
因此，该证据支持大规模恢复机制的可行性；长期运行与训练质量的规模外推仍需单独验证。
参考：[FT-HSDP 实验与质量验证](https://arxiv.org/html/2602.00277v1#S6)。

**规划判断。** 设备数量和运行时长增加会扩大故障暴露，恢复、协调及状态传输的成本成为训练效率的重要组成部分。
面向十万卡，需要将高可用机制纳入训练协议、通信和运行时设计，并考察持续运行中的有效产出。

### 5.2 关键挑战

- 一处设备、进程或链路故障可能传播到多个通信组，使大量健康设备等待。
- 资源替换、通信初始化、状态加载及首次执行都可能形成恢复长尾。
- 成员退出与重新加入会影响梯度聚合、数据进度及训练状态一致性。
- 健康监测、日志和协调机制本身需要具备规模扩展能力，避免集中式管理瓶颈。
- 慢节点、存储退化和间歇性异常可能长期消耗资源，却不直接触发进程退出。

### 5.3 技术竞争力目标

> 构建面向十万卡级训练作业的分层容错运行时，支持故障域隔离、健康部分持续训练、故障部分高效恢复与重新加入，
> 在约定故障模型下保持训练质量与有效产出，降低故障影响范围、回滚损失和长期资源浪费。

局部恢复单位需与 DP 副本以及 TP、CP、EP、PP 依赖一致。
在具备完整状态或冗余条件的故障域内推进局部恢复；对不满足条件的场景保留正确的整作业恢复路径。
集群调度、资源替换、网络和存储能力通过明确接口协同建设。

## 6. 能力四：多核并行开发框架——执行性能与新算子开发效率

### 6.1 2027 年趋势

**公开信号。** Dist-MoE 已提供用于训练前向与反向的融合通信计算实现。
昇腾在 2026 年公布的 Ascend C 升级强调 SIMD/SIMT 混合编程及面向 tile 的 PTO 指令，
进一步扩大核级计算、搬运和通信协同的空间。
参考：[Dist-MoE](https://github.com/meta-pytorch/dist_moe)、
[昇腾编程能力升级](https://www.huawei.com/en/news/2026/9/hc-agentic-thinkpro-pto-cann)。

**规划判断。** 新模型持续引入新算子与融合模式，训练性能竞争进一步涉及核级分工和细粒度调度。
高性能实现需要可复用的开发框架，以降低新算子从算法设计到训练可用、再到性能达标的成本。

### 6.2 关键挑战

矩阵计算、向量处理、数据搬运和通信具有不同执行特征。
要充分重叠这些任务，需要处理核分工、tile 切分、缓冲区生命周期和事件依赖。
逐个手写这些系统逻辑，会增加新算子的开发、验证、调优和跨硬件代际迁移成本。
前向性能优化还需要与反向、梯度累积、内存策略和低精度训练共同验证。

### 6.3 技术竞争力目标

> 建立可编程、可组合、可调优的多核并行开发框架，通过任务抽象、自动调度和公共机制复用，
> 同时提升执行性能与新算子开发效率，使开发者快速完成新算子的正确实现、性能优化和训练集成。

框架面向芯片内异构计算核，并衔接跨卡通信。
开发者描述计算语义、必要计算内核及任务依赖，由框架承担通用的核映射、任务编排、内存规划和执行生成。

**现有基础。** Multicore 已有 MoE 前后向融合、任务图、调度和 Torch 接入基础。
2027 年重点扩大框架复用范围、完善调优与验证工具，并根据实际收益扩展代表场景。
参考：[Multicore 使用指南](../hyper_parallel/core/multicore/README.zh.md)、
[Multicore 架构设计](../hyper_parallel/core/multicore/docs/architecture.zh.md)。

## 9. 阶段门槛与立项条件

### 9.1 探索性能力的推进门槛

Agent 自动优化、动态并行调度、局部恢复、弹性续训和跨场景多核调度按以下顺序扩大覆盖：

1. 在限定模型、硬件和负载下验证语义、状态及数值正确性。
2. 测量实现开销、开发成本与端到端净收益，确定适用边界。
3. 达到约定条件后，扩大模型、硬件、优化组合和集群规模的覆盖。

### 9.2 立项时需要确定的输入

- 目标用户、模型、训练任务、数据及负载分布。
- 目标 GPU/NPU 平台、互联拓扑、集群规模和存储条件。
- Codegen 覆盖矩阵、个性化框架范围、Agent 任务集与二次开发验收任务。
- 世界模型代表架构、训练路径、模态范围及有效工作量口径。
- 新算子与融合子图清单、性能门槛及手写流程对照基线。
- 十万卡设计、仿真和实机验证的资源计划、故障频率、持续运行时长及允许进度损失。
- 各工作包负责人、人力投入、跨团队依赖、量化目标和季度交付边界。

量化目标基于上述范围与基线确定，不将单个模型或实验的收益直接推广到全部场景。
