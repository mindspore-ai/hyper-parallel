# 训推一致实现指导大纲

适用于 **HyperParallel（HP）已经可以正确训练、需要接入 vLLM rollout** 的模型。交付时应能回答三个问题：哪组执行路径对同一 token 给出逐位相同的概率，哪些训练适配经过非零梯度验证，完整模型在目标机器上能承受怎样的请求负载。支持范围按模型版本、精度、设备、软件版本和拓扑组合记录。

本文用于决定新模型怎样接入、何时可以上线。Qwen3 的现有能力、实现细节和复现命令分别见[Qwen3 统一执行实现](unified_execution_guide.md)和[一致性示例](../examples/consistency/README.md)。

## 已验证组件的复用

新模型复用已有 HP 组件时，在训练配方中声明需要的替换即可。HP 完成模型构造和 TP/SP 切分后，rollout 在图捕获前遍历实际模块，为兼容的 GQA 绑定融合的 `project_qkv`，为行投影绑定推理 PIK。GQA 的 `forward` 和输出投影仍通过 HP 的入口执行。接入新模型时，应通过实际 worker 构造入口检查绑定结果。[worker 组件绑定](../rl/unified_execution/vllm/qwen3.py)

- **组件证据可复用。** 对相同算术和已覆盖的设备、精度、布局、并行规约，沿用组件的逐位、图回放与性能证据。比如任意替换产生的 `PikLinear` 都能使用同一个两叶规约，实际命中由绑定后的 TP 组、叶布局和传输方式决定。
- **模型接线只需轻量核对。** 确认实际替换覆盖、权重映射及运行时分支，用一组真实 token 核对完整链路。相同组件迁移无需逐模型重复整套算子测试或性能矩阵。
- **扩展边界时补相应实验。** 例如改变 RMSNorm 权重的舍入位置、RoPE 布局、head 维度或 collective 的加法次序时，为变化的组件补充针对性对照。相同字段名不足以证明两种实现等价。

## 开工时确定比较对象和性能目标

**数值基线。** 保存一小组可重放的真实请求：checkpoint 和策略版本、tokenizer 版本、原始 prompt IDs、实际 response IDs、逻辑位置、文档边界、action mask、采样配置、rollout 自身返回的逐 token log-prob 及其 dtype。用固定 token 做 teacher forcing，避免随机采样分叉后比较了不同的上下文。至少包含短序列、跨 chunk 或 KV 页边界的长序列，以及同一请求单独和混批执行的样本。

**概率口径。** 在同一策略版本和逻辑位置上，比对相同前缀下实际采样 token 的条件 log-prob。明确比较原始模型策略还是经过 temperature、top-k、top-p 等变换的采样策略，明确词表归一化、gather 和 dtype 转换顺序。排除 padding、观察 token 和跨文档的虚拟 label。推理和 Actor 各自产生数值；保留原始位模式（通过连续张量的 `uint8` 字节视图比较，覆盖符号零差异），在约定输出 dtype 上逐 token 比较，记录有效 token 数和首个不同位置。抽取固定位置保存完整 logits，可区分模型前向偏差与最后的概率计算偏差。异步流程按样本实际使用的策略版本回放。

**性能目标。** 先用同模型的 native vLLM 在目标硬件建立基线，再由使用方给出生产负载和预算。至少指定输入/输出长度分布、并发或到达率、真实请求占比、cache 命中条件、可用卡数，以及可接受的吞吐、尾延迟和显存。若 native 尚未支持该模型，选一个可复现的服务基线，注明来源，保留未来补齐 native 对照的空位。尚无业务预算时可以交付性能曲线，生产达标状态留待判定。

## 第一步：共享模型定义，打通加载和发布

1. 用现有 HP 训练入口取得最小可运行拓扑上的参考 forward、loss 和非零梯度。能放下时从单卡开始；必须分片的大模型可用保留完整专家、头数和状态维度的裁层模型定位问题，再用完整 checkpoint 验证。
2. 在 [models](../rl/unified_execution/models/) 声明模型族、builder、特殊层与投影位置。在 [vLLM 插件](../rl/rollout/vllm_plugin.py) 注册推理入口，由 worker 按自己的拓扑构建模型。训练配方在 RL YAML 中显式声明。模型骨架和逻辑参数语义复用 HP；用于一致性的运行时适配放在 [unified_execution](../rl/unified_execution/)，保持公共训练源码可独立使用。
   对目标镜像已有实现的 Attention、MoE、GDN，**从接入第一天就把 vLLM 原生完整组件作为 rollout 的首选候选**。先在原生 worker 记录实际命中的后端、输入输出布局、状态和计时，再在共享 decoder 的一层接入相同组件。保留原生的调度、缓存、图和可用的融合路径，记录桥接所需的重排、通信及权重预打包成本。缺少目标设备或拓扑实现时，以已验证的共享后端起步。
3. 为每组融合或共享参数及影响前向的持久 buffer 写清“逻辑名称和切片 → 目标 rank → 本地布局 → 写入对象”。重点核对 Q/K/V 头排列、gate/up 的打包顺序、expert ID、词表 padding、权重别名，以及路由偏置（如 FP32 `expert_bias`）或缩放等非参数状态以原精度同步。每个推理参数或状态只由一个 loader 负责分片；若用 native 组件接管物理布局，也由该组件负责原址刷新预打包存储。[加载边界](../rl/unified_execution/vllm/weight_loader.py) · [发布协议](../rl/weight_sync/)
4. 分别验证从 checkpoint 冷启动和在线发布。用一次确实改变专家或投影参数的更新，核对目标 shard 的字节或逆布局后的逻辑张量、所有预期接收者的确认和可服务的策略版本，再用同一 token 前缀重放。覆盖 sleep/wake、旧版本 KV 或递归缓存失效、新版本首个请求。发布中断时验证服务不会暴露混合版本；恢复或回滚后再开放采样。

**通过条件**是同版本的初始权重与更新后权重都能对照，最小拓扑的固定 token 前向有可复现基线。记录参数变化量、发布版本及接收者；奖励全零的两步 RL 可以验证流程，非零更新另行举证。

### 用下一个模型检验适配边界

模型族负责三件事：识别层与逻辑参数，解释特殊组件的状态，定义逻辑权重到原生组件的映射。共享代码负责按同一组 token 运行对照、核对策略版本并定位首个差异。当前模型族已有注册入口，Attention 校验和专家 loader 中仍有 Qwen3 专属判断。接入结构不同的模型时，把实际遇到的差异放回所属模型族，再根据两个模型共同需要的操作提取接口。[模型族注册](../rl/unified_execution/models/registry.py) · [结构校验](../rl/unified_execution/models/structure.py) · [权重 loader](../rl/unified_execution/vllm/weight_loader.py)

例如接入带 GDN 的混合模型，模型适配提供卷积状态、递归状态和 chunk 边界的读写方式，沿用同一套执行与比较流程。验收记录同时列出改动涉及的共享文件及原因、直接复用的测试，以及从发现概率偏差到定位首个分叉所用的时间。这些记录用于判断哪部分值得通用化。

## 第二步：对齐四条前向路径，及早验证图执行

进入多卡切分前，先在 `TP1/EP1/CP1`（大模型用第一步的裁层模型）对齐下面四条路径，把单卡算子与概率出口偏差同跨卡规约问题拆开。

| 执行位置 | 最小实验 | 首先排查的差异 |
| --- | --- | --- |
| rollout decode | 保存每一步输入、实际 action 和推理 log-prob | 采样前后概率语义、runner 专属 `log_softmax` 实现、KV/递归状态更新、位置偏移 |
| rollout prefill | 对同一续写做 teacher forcing，再改变 chunk 切点、混批顺序和 prefix 命中 | 因果 mask、页映射、Attention 分块与尾块规约、缓存精度、runner 概率出口 |
| Actor 评分 forward | 在同版本权重上按原 token、位置和 mask 独立重算 | packing 边界、next-token 移位、词表归一化 |
| Actor 训练 forward | 在定义好的随机性策略下启用 autograd，核对用于 loss 的 action 概率，并运行非零反向 | 训练专用分支、融合、激活重算、梯度同步与 loss 缩放 |

**结构检查与最终执行检查分两次做。** 当前 Qwen3 推理入口先调用 `capture_training_structure()` 核对 HP 模型，再安装分页 Attention 桥接。保留这项检查以发现建模和参数映射偏差。对于后来替换或融合的组件，建议在安装完成后记录各执行位置实际绑定的实现，首次图捕获或重放时补记按输入档位选择的实际后端。[当前安装顺序](../rl/unified_execution/vllm/qwen3.py)

每条记录关联逻辑层、输入输出的 token/head/expert 身份、权重 shard 与版本、累加 dtype、规约和舍入点、实际调用的实现以及适用拓扑和图档位。例如对 MoE 的 combine，应能查到某个 token 的贡献来自哪些 top-k 槽、在哪一步乘 router 权重，以及该次运行由哪个后端完成合并。训练与推理可以绑定不同实现，分别核对各自的绑定与声明，再用固定输入检验两者的数值。启动时的结构或配方指纹通过，只能覆盖其实际检查的范围。

先定位 decode 与 prefill 的第一个不同 token，再比较 prefill 与 Actor 评分，最后比较评分与训练 forward。固定输入逐层定位时，依次截取输入激活、投影、位置编码、Attention 或状态更新、router/专家槽位、残差和词表头；把首个不同张量连同 shape、stride、位置及实际 kernel 留作回归样本。

根据首个差异选择修改范围：

- **原生组件与 HP 已对齐。** 在目标 batch、图档位和并行组合验证通过后，直接采用原生组件，并验证其 loader 在策略更新后刷新全部副本。
- **原生推理自身稳定，与训练有差异。** 若原生算术在目标拓扑间也稳定，优先评估在 RL 训练适配层复现其 forward 的累加和舍入。用独立反向参考及非零更新检查梯度，并测训练 tokens/s 和显存。若差异仅来自一个 cast 或 combine，而在推理侧修这一处更便宜，则保留原生组件其余部分。
- **原生 prefill/decode、混批或跨拓扑自身分叉。** 先定位第一个改变结果的规约或状态更新。用最小可替换后端统一这段计算，推理继续使用原生缓存、metadata 和已通过的算子。训练无法同时匹配同一输入的两个不同结果。

为各执行位置选定一种已验证的 batch-invariant 实现，记录每个实际 worker 使用的后端、累加精度和舍入点。HP 当前的 TorchNPU Level 3 路径与 vLLM-Ascend 全局 batch-invariant 替换有显式冲突检查。单条请求、重复运行、改变 batch 形状和跨执行位置的逐位对照分别验证不同性质。[数值策略](../rl/unified_execution/batch_invariant.py) · [执行契约及校验](../rl/unified_execution/contract.py)

先过 eager 对照，随后立即捕获最小图，原地更新输入、路由、序列长度或状态并重放。覆盖图档位边界和合法大 batch，记录实际命中的完整图、分段图或 eager 路径；图编译和 kernel 融合可能改变算术。训练前向保持逐位要求；被 RL 替换的训练计算用独立参考比较输入与参数梯度，按 dtype 预先声明容差，并检查非零优化器步。梯度跨并行规模允许合理的浮点累加差异。

## 第三步：确定并行所有权，逐轴扩展

vLLM 负责 rollout 请求归属、原生进程组、调度、缓存和图生命周期。HP 提供训练并行和共享模块的参数布局。RL 在二者之间约定逻辑 token、head、expert、权重 shard 的身份，以及哪些地方发生浮点加法。推理根据自己的 TP/DP/PCP/EP 配置解释这些身份。[worker 并行域构建](../rl/unified_execution/vllm/parallel_context.py)

| 轴 | 应固定的含义 | 有判别力的对照 |
| --- | --- | --- |
| TP / SP | K 维逻辑分块、部分和精度、规约树与最终 cast；SP 的序列行归属 | 基线与不同 TP 度、SP 开关比较相同全局位置；单独检查行并行投影。可选固定逻辑叶子的树，或通过重排获得完整 K 维 GEMM，按实测选型 |
| DP / FSDP | 样本、有效 token 数与参数逻辑身份 | 改变 batch 分配或参数 shard 后比较同一样本，检查副本均收到新权重；验证梯度平均与 loss 分母 |
| 训练 CP / 推理 PCP | 全局位置、可见 KV 前缀、mask、分片边界及可能的 softmax 部分和 | CP1/PCP1 保留原路径；分别只开训练 CP、只开推理 PCP，再比较目标组合。空 rank 参加必要通信；DCP 另列支持项 |
| EP | 全局专家 ID、top-k 并列规则、槽位、router 权重精度、权重相乘和合并顺序 | 固定 routes/scores 比 expert-major 输出及每槽贡献，再恢复真实 router。覆盖空专家、偏斜、跨 PCP 专家域和容量边界 |
| 其他目标轴 | 如需 PP、量化、专家内部 TP，另列 stage 边界、scale 或部分和语义 | 在目标模型上分别验证后加入支持矩阵，记录不支持项及运行前拒绝条件 |

从并行度为 1 的已知基线开始，每次改变一个轴，最后跑**训练和推理使用不同拓扑**的实际部署组合。模型过大时以裁层模型补足单轴诊断，完整模型验证目标组合。交付时在矩阵中分别标明前向位比较、训练梯度、在线发布、图执行和性能通过的配置。

## 第四步：优化原生候选与共享后端之间的性能差距

| 组件 | 建议从哪一侧开始 | 最小决定性实验 |
| --- | --- | --- |
| GQA Attention | 复用 HP 模型的投影和位置语义，推理优先使用 vLLM 的分页 KV、调度和原生写入 | 同一 Q/K/V 上比较 dense、varlen、paged 和 CP 前缀；分别计时 Q/K norm＋RoPE、KV 写入、metadata、Attention 核心和输出布局，决定替换哪一段 |
| MoE | 训练沿用可微路由；rollout 先测完整 native MoE，出现差异后再分解 router、dispatch、专家计算及 combine | 在同一个 decoder、同调度和同一层真实权重下，只换一层 MoE。固定 IDs 和 FP32 scores，分别比 dispatch 后的有效行、专家输出、combine 后的结果。先测小 decode、高并发和长 prefill，再跑全模型 |
| GDN 等递归结构 | 优先确定 native decode 的状态转移、卷积缓存及写回精度 | 同一非零初态依次跑整段 prefill、不同 chunk 切分、逐 token decode，每个切点同时比输出和下一状态。推理内部对齐后，训练 chunk forward 对齐同一状态语义，并独立检验跨 chunk 反向 |
| 线性层、norm、词表头 | 默认复用现有 HP 实现；融合或复用推理 forward 按收益选择 | 在实际 dtype、shape、stride 和极值输入下核对 cast、残差加入点、log-softmax 和选定 token；训练采用推理 forward 时提供并验证其 backward |

MoE 的固定路由样本应包括真实 router 输出的非均匀 FP32 权重，覆盖同一 token 的多个专家分布在不同 rank 的情况。相等的 top-k 权重可能掩盖权重提前转低精度或乘法位置变化；固定 ID 的组件实验完成后，再打开原生 router 对照选出的 ID 和权重。

以 MoE 为例，若首次差异在 combine，就单独替换 combine，继续测原生 dispatch 和 GMM。若差异源于 top-k 的并列顺序，先修 router。若组件 kernel 已加速而整层耗时没有改善，在同一 trace 中核对入口和出口的重排、额外 gather、cast 和图断点。若开销集中在这些边界，把相邻操作纳入同一候选；跨组件融合确有必要时，再把原生 decoder block 和共享 block 放在同一调度器内对照。扩大替换范围后重新验证残差顺序、权重发布与图重放，并用完整请求和 RL step 的净收益决定保留范围。每次试验保留原路径作为参考，使用相同权重和逻辑输入，每通过一项就在整模型固定 token 和图重放上回归。采用另一种通信或融合实现的依据是**数值、图和完整业务负载**三项证据。

图内通信根据全组一致的调度元数据选择缓冲上界，设备上的动态计数控制有效工作量。容量只限定相应快速路径；合法大 batch 在通信开始前选择已验证的替代路径。以空 rank、容量上下各一行和变更权重后的图重放，检查无丢 token、陈旧地址或错误集体通信。

## 生产性能与放行

为每个目标负载在开工时填入下表的预算，记录单位和可接受波动。吞吐按成功返回的有效输出 tokens 除以整组墙钟时间计算。线上有时限的场景同时统计**满足时限的请求数/秒**及超时率，避免只看平均 tokens/s。

| 负载 | 对照条件 | 放行指标 |
| --- | --- | --- |
| 短 prompt、小 batch decode | 相同模型、硬件、并发、输出预算与 EOS 策略 | 总输出 token/s、每请求 TPOT、p95/p99 延迟 |
| 高并发连续到达、长短混批 | 固定到达分布、队列上限、调度预算、cache 命中率 | 满足延迟预算的最大吞吐、排队和超时、峰值 HBM |
| 长 prefill、长 KV decode、多轮或状态复用 | 分别控制输入和输出长度、chunk、prefix hit/miss | 首 token 延迟（TTFT）、后续 TPOT、每卡 KV/状态容量 |
| 完整 RL 步及持续运行 | 真实采样预算、训练拓扑、非零更新与发布频率 | 有效训练 token/s、step 时间、发布时间、sleep/wake 或重启后正确性、长跑显存与错误率 |

保留两组基准：**同等资源的 native 服务**衡量性能差距，**已验收的 unified 版本**衡量改动的收益和回退。固定镜像和权重指纹、精度、采样设置、图档位、KV 配额及 CPU 线程；列出实现所必需的不同设置。预热后无 profiler 重复测量，记录中位数、离散度与尾延迟，主要结论用独立启动复核。冷启动、图捕获开销及图显存单列。profile 另跑，区分 CPU 等待、设备计算和通信重叠。性能结果附样本量，尾延迟用符合生产到达分布且足量的请求统计。

放行前逐行填写目标值、实测值和证据位置。例如在线 decode 可约定“每卡成功输出 token/s ≥ 业务下限，p99 TPOT ≤ 延迟上限，峰值 HBM ≤ 容量预算”；整步 RL 另列单位时间有效训练 token 和发布时延。若团队采用 native 吞吐占比作为目标，按同负载的 unified 吞吐除以 native 吞吐计算。分别判断每项关键负载，保留未达标项及后续实验。
