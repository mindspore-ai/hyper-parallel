# Kimi-K2.6 Codegen Bundle — Validation Fix Record

This directory hosts the codegen artifact bundle for `kimi_k26`
(`modeling_Kimi_K25_gen_npu.py` + `codegen_meta.json`, regenerated by
training with `codegen: true`).

This file documents the **nine fixes** that were required to make the frozen
dual-arm precision validation pass for Kimi-K2.6 on 8x Ascend 910B3
(`examples/training_demo/codegen_validation/run_codegen_validation.sh`,
`RUN_KIMI=1`; pytest entry: `tests/torch/codegen/kimi_k26/`).

> **NOTE:** `generated/` is rebuilt atomically by the codegen writer
> (`write_bundle_atomic` replaces the whole directory), so re-running codegen
> generation removes this hand-written file. The canonical copy lives in git
> on branch `kimi_k26_codegen` — restore it with
> `git checkout kimi_k26_codegen -- hyper_parallel/models/kimi_k26/generated/KIMI_K26_CODEGEN_FIXES.md`.

## Validation scenario

| Item | Value |
| ---- | ----- |
| Host | 8x Ascend 910B3, single node |
| Parallel geometry | `tp=1, cp=1, ep=2, pp=1, dp_shard=4, edp_shard=1` |
| Cropped model | `num_hidden_layers=2`, `n_routed_experts=8`, frozen vision tower (`freeze_patterns: ["model.vision_tower*"]`) |
| Entry | `torchrun --standalone --nproc_per_node=8 --module scripts.train_vl <yaml>` |
| Determinism | `seed: 42`, `enable_full_determinism: true` |

Fixes #1, #2 and #5 are **kimi_k26-scoped** (offline validation assets /
cropped validation model). Fixes #3, #4, #6, #7 and #9 are **core library
bugs** that affect any model hitting the same path — not 8-card or
kimi-specific. Fix #8 works around a core DTensor op-registration gap at the
validation-builder level so that both arms initialize identically.

## Fix #1 — Offline tokenizer media token ids must match the checkpoint

- **Scope:** kimi_k26 validation assets (`examples/training_demo/codegen_validation/kimi_k26_assets.py`)
- **Symptom:** The cropped model's `get_placeholder_mask` scans the input
  stream for `config.image_token_id` (163605). The offline WordLevel
  tokenizer assigned freshly-allocated ids to the media protocol tokens
  (`<|media_pad|>` etc.), so no position in the stream ever carried the pad
  id the model scans for — the image features had no insertion anchor and
  the first step failed.
- **Root cause:** The synthetic tokenizer was built without pinning the
  media token vocabulary, and the config copy side did not keep the
  checkpoint's media ids.
- **Fix:** Pin the canonical hub media token ids in the offline vocab
  (`_CANONICAL_MEDIA_TOKENS`: begin=163602, content=163603, end=163604,
  image pad=163605, video=163840), declare them via
  `additional_special_tokens`, and have `prepare_config` copy the config
  keeping `image_token_id` / `video_token_id` unchanged so
  `KimiVLMChatTransform._media_ids` is a no-op remap.
- **Files:** `examples/training_demo/codegen_validation/kimi_k26_assets.py`

## Fix #2 — Cropped expert count must shrink the MoE group geometry

- **Scope:** kimi_k26 validation builder
  (`hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`)
- **Symptom:** First forward step aborted in the NPU top-k kernel with
  `aclnnTopk ... EZ1001`.
- **Root cause:** Cropping `n_routed_experts` 512 -> 8 left `n_group` at its
  source value, giving fewer than 2 experts per group. The native
  `DeepseekV3MoEGate` ranks each group by the sum of its **top-2** expert
  scores; with a size-1 group the per-group `topk(2)` addresses an empty
  dimension and the kernel rejects it.
- **Fix:** New `crop_moe_group_geometry(n_routed_experts, n_group,
  topk_group, num_experts_per_tok)` derives a legal group pair: the largest
  group count that divides the expert count with >=2 experts per group
  (8 experts -> `n_group=4, topk_group=2`), preserving the selected-group
  fraction, then widening the selection until the surviving experts can
  still feed `num_experts_per_tok`. Applied in `_load_cropped_kimi_config`
  and mirrored on the assets side (`kimi_k26_assets.prepare_config`) so the
  generated `model_config` and the codegen bundle agree.
- **Files:** `hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`,
  `examples/training_demo/codegen_validation/kimi_k26_assets.py`

## Fix #3 — `init_unsharded_param` must run under `no_grad` (core)

- **Scope:** core HSDP (`hyper_parallel/core/fully_shard/hsdp_param.py`)
- **Symptom:** `RuntimeError` from autograd's mixed-mode view check during
  backward — a view materialized inside a no-grad region tripped over an
  inplace write recorded in grad mode on the same buffer history.
- **Root cause:** `HSDPParamV2.init_unsharded_param` built the stable
  unsharded parameter (all-gather copy + `as_strided` view) without the
  `@torch.no_grad()` guard its siblings (`_init_sharded_param`,
  `_get_unsharded_param_data`) already carry. It is pure data movement for a
  leaf parameter, never forward computation, so recording it in autograd is
  wrong and — under activation checkpointing, where regions alternate
  grad/no-grad — produces views that violate the mode-consistency check.
- **Fix:** Decorate `init_unsharded_param` with `@torch.no_grad()`.
- **Files:** `hyper_parallel/core/fully_shard/hsdp_param.py`
- **Trigger condition:** HSDP + activation checkpoint + any parameter whose
  unsharded view gets built across different grad modes (model-agnostic).

## Fix #4 — Frozen units must not be prefetch targets (core)

- **Scope:** core FSDP adapter
  (`hyper_parallel/distributed/_builder/fsdp_adapter.py`)
- **Symptom:** `Unconsumed prefetch handles` raised by the root backward
  hook (`check_state_prefetch_handles_consumed`); all 8 ranks aborted after
  the first backward.
- **Root cause:** Two independent assumptions of `_configure_prefetch`
  break when a unit's parameters are **all frozen** (here: the vision tower
  under `freeze_patterns: ["model.vision_tower*"]`):
  1. *Frozen units never run a backward pre-hook* — autograd skips them
     entirely (their forward output does not require grad), so any
     all-gather issued as a **backward prefetch target** for them is never
     consumed.
  2. *Wrap-list order != execution order for frozen vision attention* — in
     `named_modules` order the attention `proj` unit precedes its
     `q/k/v_proj` units, but the runtime executes q -> k -> v -> proj. The
     `proj` unit's forward pre-hook therefore issued forward-prefetch
     all-gathers for `q/k/v` **after** their last forward — combined with
     (1), those handles could never be consumed either.
- **Fix:** `_configure_prefetch` now filters both prefetch chains with a new
  `_participates_in_backward(hsdp_module)` predicate (true iff the unit owns
  at least one parameter with `requires_grad=True`):
  - forward prefetch targets only units that participate in backward;
  - the backward prefetch chain is built over participating units only;
  - frozen units are never prefetch targets — their own forward pre-hook
    unshards them synchronously.
- **Files:** `hyper_parallel/distributed/_builder/fsdp_adapter.py`
- **Trigger condition:** FSDP/HSDP with `forward_prefetch_depth > 0` or
  `backward_prefetch_depth > 0` **and** a partially frozen model (typical:
  VLMs with a frozen vision tower). Card count is irrelevant.

## Fix #5 — `build_cropped_kimi_vlm` must accept and forward `codegen`

- **Scope:** kimi_k26 validation builder
  (`hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`)
- **Symptom:** The codegen arm completed 10 steps with `max_diff = 0.0`
  against native — but the three `codegen:` criteria log lines
  (`generating artifact` / `imported generated modeling file` / `sharding
  applied by the generated module`) were **absent**.
- **Root cause:** `trainer/config/target.py:Target.build()` filters the
  runtime kwargs it forwards by the target function's signature: kwargs the
  function does not declare are dropped **silently**. The validation model
  builder `build_cropped_kimi_vlm` predated the codegen knob, so its
  signature had no `codegen` / `codegen_config` parameters — the trainer's
  `codegen: true` never reached `HyperAutoModelForImageTextToText.from_config`,
  and the "codegen" arm silently trained the native model. The reported
  `max_diff = 0.0` was therefore a **false positive** (native vs native).
- **Fix:** Add `codegen: bool = False` and `codegen_config: Any | None =
  None` parameters to `build_cropped_kimi_vlm` and
  `_build_cropped_kimi_model`, forward them into
  `HyperAutoModelForImageTextToText.from_config(...)` (docstring notes the
  `Target.build` signature-filtering contract).
- **Files:** `hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`
- **Trigger condition:** Any model-builder target that predates the codegen
  knob (silent `codegen` drop). With this fix the codegen path executes and
  the real generated-module bugs below became observable.

## Fix #6 — Architecture-name normalization in the codegen loader (core)

- **Scope:** core codegen loader (`hyper_parallel/codegen/loader.py`)
- **Symptom:** `AttributeError: generated module ... has no class
  'KimiK25ForConditionalGeneration'; defined classes: [...,
  Kimi_K25ForConditionalGeneration, ...]`.
- **Root cause:** The HF checkpoint's `config.json` records the
  architecture as `KimiK25ForConditionalGeneration` (no separators), while
  the transformers class — and hence the generated modeling file — is named
  `Kimi_K25ForConditionalGeneration`. `resolve_generated_model_class`
  matched by exact `getattr` only.
- **Fix:** After the exact-match lookup fails, fall back to a normalized
  comparison (strip `_`, lowercase) over the module's exported classes.
- **Files:** `hyper_parallel/codegen/loader.py`
- **Trigger condition:** Any checkpoint whose `architectures[0]` spelling
  differs from the transformers class name.

## Fix #7 — `verify_param_plan` must exempt tied weights (core)

- **Scope:** core codegen preflight (`hyper_parallel/codegen/check/preflight.py`)
- **Symptom:** `RuntimeError: codegen preflight: 1 trainable parameters
  are not covered by the frozen plan: ['lm_head.weight']`.
- **Root cause:** `codegen_meta.json` records the tie
  `["model.language_model.embed_tokens.weight", "lm_head.weight"]`
  (`tied_pairs`). The frozen param plan covers the canonical side
  (embed_tokens, tp `S(0)`); the non-canonical `lm_head.weight` is materialized
  by the tie and has no plan entry of its own. `verify_param_plan` required
  every trainable parameter to have a plan entry, so the tied side failed.
- **Fix:** `verify_param_plan` now collects the non-canonical side of every
  `tied_pairs` entry via a new `_expand_tied_param_names(meta)` helper and
  exempts those names from the uncovered-parameter check.
- **Files:** `hyper_parallel/codegen/check/preflight.py`
- **Trigger condition:** Any generated model with tied weights
  (embedding/lm_head tying is common).

## Fix #8 — `trunc_normal_` breaks DTensor init in the generated module

- **Scope:** kimi_k26 validation builder
  (`hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`)
- **Symptom:** `RuntimeError: Operator new_tensor does not contain parallel
  layout infer func` during model build, raised from the generated file's
  `Kimi_K25VisionPositionEmbeddings` init.
- **Root cause:** `torch.nn.init.trunc_normal_` internally chains
  `new_tensor` / `erfinv_` / `item` / `uniform_` — none of which have a
  HyperParallel DTensor layout-inference registration, so the first op deep
  in the chain raises from `_handle_unregistered_op` when the parameter is
  already a sharded DTensor. The native arm avoided this via its
  `_init_weights` monkey patch (swapping in `normal_(std=0.02)`), but the
  generated bundle is an independent modeling file with its own class
  definitions — the patch on the transformers module cannot reach it.
- **Fix:** Refactor the native patch into a `_make_patched_init_weights`
  factory that dispatches on the **class name** (matches both the native
  and generated families), and — for the codegen arm — wrap
  `codegen.loader.import_generated_module` so that, right after the
  generated module is imported, the same patch is installed on the
  generated module's own `Kimi_K25PreTrainedModel._init_weights`. Both
  patches are restored in `finally`. This keeps both arms' random
  initialization **identical** (same `normal_(mean=0.0, std=0.02)`
  substitution), preserving the dual-arm comparability.
- **Files:** `hyper_parallel/models/kimi_k26/adapter/validation/cropped_model.py`
- **Trigger condition:** Any DTensor-sharded parameter initialized through
  `trunc_normal_` on a path without the native patch. (The underlying gap —
  init deep-chain ops lack DTensor layout registration — is a known core
  limitation; registering each op individually is not tractable, hence the
  initialization-level workaround here.)

## Fix #9 — `init_generated_model` drops `torch_dtype` on the from-config route (core)

- **Scope:** core codegen loader (`hyper_parallel/codegen/loader.py`)
- **Symptom:** `RuntimeError: Input type (c10::BFloat16) and bias type
  (float) should be the same` in the first conv2d of the generated
  `Kimi_K25VisionPatchEmbed.forward` — the model built in float32 while the
  batched `pixel_values` were bfloat16.
- **Root cause:** `init_generated_model(artifact_dir, ..., torch_dtype
  = "auto", **kwargs)` captures `torch_dtype` as a named parameter, so it
  never lands in `**kwargs`; the from-config branch then called
  `model_cls._from_config(hf_config, *model_args, **kwargs)` **without**
  the dtype. The native path (`model_builder._init_model`) passes
  `config_kwargs["dtype"] = torch_dtype` into `_from_config`, where
  transformers >= 5.14 resolves it onto the config and every subconfig
  before instantiation. Without it the generated model defaulted to
  float32.
- **Fix:** New `_with_dtype_kwarg(kwargs, torch_dtype)` helper forwards
  `dtype` into the `_from_config` call on **both** loader branches
  (from-config and checkpoint), mirroring the native route's
  `if torch_dtype != "auto"` guard (`"auto"`/`None` are not forwarded;
  transformers resolves them from the config).
- **Files:** `hyper_parallel/codegen/loader.py`
- **Trigger condition:** Any from-config (random-init) codegen build with a
  non-float32 `torch_dtype` — i.e. every training-style validation.

## Validation result

> **Correction of an earlier claim:** the first "passing" report after fixes
> #1–#4 (`max_diff = 0.0`) was a **false positive**: fix #5 had not landed
> yet, so the `codegen: true` kwarg was silently dropped and both arms
> trained the *native* model. The results below are from the run where the
> codegen arm verifiably executes the generated module.

Final frozen-script run (`run_codegen_validation.sh`, `RUN_KIMI=1`) —
all 11 checks PASS, including the three codegen-execution criteria in the
codegen-arm log:

```text
codegen: generating artifact .../kimi_k26/generated (signature 5883174ce5b4)
codegen: rendered bundle .../kimi_k26/generated (modeling modeling_Kimi_K25_gen_npu.py, 37 plan boundaries)
codegen: imported generated modeling file .../modeling_Kimi_K25_gen_npu.py
codegen: sharding applied by the generated module; source_shard_info keys=72
```

Both arms complete 10/10 steps and the per-step `training/total_loss`
sequences are **bit-identical** (`abs_diff = 0.0` each step, tolerance
`5e-4`): native/codegen
`6.08196, 6.08159, 6.06782, 6.06213, 6.03831, 6.04553, 6.03696, 6.03675,
6.02938, 6.02681`. Full procedure and environment:
`tests/torch/codegen/kimi_k26/TEST_REPORT.md`.
